# Task: Architecture baseline and validation

**Agent:** architect
**Type:** documentation only (no production code, tests, CI or build config)

## Why

The repository has one ADR (`docs/adr/0001-tech-stack.md`) and an initial scaffold in
`crates/app-core`, `crates/engine`, `src-tauri` and `ui`. Before feature work starts we need:

1. a validated picture of what the code actually does versus what ADR-0001 and `CLAUDE.md` say, and
2. the missing architecture decisions written down, so `backend` / `frontend` / `devops` can build
   features without guessing.

## Scope

### A. Validate the current architecture

Read `CLAUDE.md`, every file in `docs/adr/`, and the code in `crates/`, `src-tauri/src/`,
`src-tauri/tauri.conf.json`, `ui/src/` (especially `bindings.ts`, `ipc/`, `stores/`) and
`.github/workflows/`. Check the code against every architecture rule and hard constraint in
`CLAUDE.md` and against ADR-0001, including at least:

- project model lives in Rust; every model change is a command with undo/redo; no model logic in TS
- video frames never cross JSON IPC; preview rendered natively by wgpu; `media://` for thumbnails
- preview and export share one render graph (or the current code leaves room for that)
- audio thread real-time rules (or the plan for them, if audio does not exist yet)
- effects as data (`effect.json` + `shader.wgsl`)
- time as `i64` flicks in the model and IPC, never `f64` seconds (check `bindings.ts` and `ui/src/lib/time.ts` too)
- `bindings.ts` generated by tauri-specta, not hand-written; no hand-written TS types for Rust commands
- LGPL-only FFmpeg, dynamic linking, `deny.toml` licence policy
- Windows x64 shipping path (NSIS `currentUser`, updater) and Linux ARM64 dev path (frames preview mode)

Also note the uncommitted change in `src-tauri/build.rs` + `src-tauri/windows-app-manifest.xml`
(embedding the Common Controls v6 manifest so `cargo test` binaries start on Windows) and say whether
it fits the architecture or needs a follow-up.

Classify each finding as **OK**, **Drift** (code contradicts docs), **Gap** (decision missing or
undocumented) or **Risk** (allowed today but likely to hurt later), with file references.

### B. Prepare the architecture

- Write `docs/architecture.md`: a one-page overview of modules, ownership, threads, and the main data
  flows (command → model → undo stack → events → UI; decode → render graph → preview / export;
  audio path; `media://` path; preview window on Windows vs frames mode on Linux), with Mermaid
  diagrams. It must describe the code as it is plus the target where they differ, clearly marked.
- For each **Gap** that is a hard-to-reverse decision, write a new ADR (`Status: Proposed`) in the
  format of `docs/adr/README.md` and add it to the index. Likely candidates (only where actually
  missing): project-file format + `schemaVersion` migration strategy, IPC conventions (command naming,
  errors, events, long-running jobs with `JobId` + `job_progress`), threading model (UI / model /
  decode / render / audio), preview presentation strategy per platform, undo/redo transaction model.
  Keep them small (YAGNI/KISS); don't invent features.
- Do **not** change ADR-0001 in place. If it is wrong, propose a superseding ADR.

## Deliverables

- `docs/architecture.md`
- `docs/architecture-review.md`: validation report (findings table: area, status, evidence, recommended
  action, owning agent) plus a prioritised list of follow-up tasks for `backend` / `frontend` / `devops`
- zero or more `docs/adr/NNNN-*.md` (Proposed) + updated `docs/adr/README.md` index

## Done when

- every rule in `CLAUDE.md` "Architecture rules" and "Hard constraints" has a verdict in the report
- every Drift/Gap/Risk has a recommended action and an owner
- `docs/` contains no production code; Mermaid diagrams render; no CapCut names or assets
- the architect's summary lists any place where `CLAUDE.md` should change (the orchestrator decides)
